**Bench note, 2026-11-22.** Published on this fork for the record; **nothing here has been sent to a maintainer or a
club.** Upstream `bpx03/QEngine` is the product; this fork is a bench, and the notes are not a support offer.
Upstream's licence and headers are untouched.

Measurement host: 4 × RTX 5080 16 GB, PCIe Gen5 ×8 behind a Broadcom/LSI PEX890xx Gen 5 switch, peer access OK on

*(Drafts. Neither has been posted; both name the failing line and the command that produced it.)*

> Reproduced on a GPU now, with the fault address. Four RTX 5080, Flash-Next, the
> `1.5.0-vision` image at `d091eae`, `FLASH_PAR=tp`, `FLASH_KV=ram` + `FLASH_KV_BITS=4`,
> archive 8 GB, `FLASH_MAX_SEQS=2`, `--max-ctx 262144`. The boot line confirms the
> switch: `checkpoints every 0 tokens`.
>
> Two requests share one ~650-token system prefix (over `ckpt_min`). R1 is that system
> plus a long body: 2 198 prompt tokens. R2 is the same system, the first ~6 000
> characters of R1's body, and a different tail: 2 046 prompt tokens. R2's divergence
> point is then in the plan and is not the system end, so the kind expression runs for a
> non-periodic position.
>
> ```
> qengine: fatal signal 8 (SIGFPE) at address 0x7917ac5ec0be in thread 16809; engine job: none
>   /app/server/../build/libqflash.so(+0x3e20be)[0x7917ac5ec0be]
>   /app/server/../build/libqflash.so(qe_prefill_more_slot+0x2624)[0x7917ac5f6bc4]
> container: status=exited exit=136 oom=false
> ```
>
> A second boot dies at the same file offset (`0x…cec0be` — same low bits, different
> ASLR base). `addr2line` on the shipped `libqflash.so` puts `+0x3e20be` in `take_ck`,
> and that is the instruction:
>
> ```
> 3e20bb: mov %edx,%eax
> 3e20bd: cltd
> 3e20be: idivl 0x1404(%rdi)     ← FE::ckpt_every
> ```
>
> Control in the same shape with `FLASH_CKPT` left at 8192: both requests return. So
> `ckpt_every == 0` is the variable, exactly as the issue says.
>
> One thing the issue did not say: **`FLASH_CKPT` appears in no documentation** — not
> `docs/advanced.md`, not `README.md`, not `server/app.py`, not `bench/`. It is read at
> `flash_capi.cpp:3983`, and the engine's own plan loop treats `0` as valid, so a user
> who reaches for `0` to mean "no periodic checkpoints" gets a SIGFPE with no warning
> that the knob exists.
>
> Patch on our fork, `ss16/qe-defects` @ `34c5991` (one file, +27/−5): one classifier,
> `ck_kind()`, used at both kind sites (`:3000` and `:4562`). It asks for a period first;
> with no period nothing is periodic, so a position that is not the prompt end, the
> system end or the prompt end − 1 is kind 5 — the answer the expression already gives
> for any period that does not divide `pos`. With the patched library the two prompts
> above both return and the container stays up; the instrument-only build (same sources,
> two prints, C-API set and arch census identical to the release) dies like the release
> does, at `+0x3e23de`.

> Reproduced on a GPU. Same rig and shape; `FLASH_KV_ARCHIVE_GB=0.30`,
> `FLASH_PREFIX_GB=0.15`, checkpoints at the default. Ten distinct ~650-token system
> prompts, each of which pins `0.13 GB: KV 0.01 + state 0.12`, bodies of ~1 200 tokens,
> then one request whose system prompt is under `ckpt_min` so it writes an archive copy
> without creating a pin.
>
> The release library prints no `aused()`, so the measurement is from a build of the
> pinned source with two `fprintf` in `drop_pin` and nothing else — C-API names 102 vs
> 102 (0 added, 0 removed), `sm_86/89/120` census identical, +112 bytes. At the drop:
>
> ```
> [qflash] archive: pinned prefix 653 tokens dropped (pin budget; 0.13 GB, pinned 0.00 of 0.15 GB)
> [qflash] diag drop_pin BEFORE: aused 0.240 of 0.300 GB (pool 0.365, pinned 0.125 of 0.150 GB)
> [qflash] diag drop_pin AFTER:  aused 0.360 of 0.300 GB (pool 0.360, pinned 0.000 of 0.150 GB) OVER BUDGET
> ```
>
> The pool moved 0.005 GB while `pin_used` went to zero — the dropped prefix's **state
> blob (0.12 GB) is still held by the conversation**, so the archive's own account rose
> to 0.360 GB against its 0.300 GB budget, 20 % over, with nothing pinned and no
> `make_room`. Your fuzz model's 133–236 MB and our one state blob of 120 MB are the
> same mechanism at the same size.
>
> Two limits, so the report is not oversold:
> - **bounded by one state blob per drop.** With the archive set smaller than one state
>   (`0.12 GB`) every drop freed cleanly, because the holder was evicted first; with a
>   large archive the account landed exactly on budget (`0.480 → 0.600 of 0.600`). The
>   leak needs the sharing conversation to survive the drop.
> - **no conversation loss attributable to it.** At the identical shape the pre-fix and
>   post-fix runs printed the same `lost conversation` 9 / 9 and `archive full` 19 / 19.
>   The harm is the invariant: between a drop and the next write, every reader of
>   `aused()`/`eff_budget()` — `press_cap`, the `used + need > limit + can_free`
>   admission test, the pressure report — is reading an account that the pinned-prefix
>   budget has already stopped paying for.
>
> Patch: `drop_pin` takes the archive back to its budget at the drop
> (`make_room(0, nullptr)`, which is a no-op inside budget and evicts in the existing
> order outside it) and logs what it did. The two callers that are eviction callbacks
> inside a reclaim loop pass `enforce=false`, so nothing nests. On the cards the same
> event prints `dropped prefix still held, 0.060 GB over the 0.30 GB budget: older
> copies evicted`, and the loss counts stay 9 / 19 — the patch changes the accounting,
> not the eviction volume.
>
> While we were in there: the engine publishes `archives.pinned_bytes` (page-locked
> bytes) but never `pin_used` or `aused()`, so this class of bug is invisible from the
> outside without a rebuild. A `pinned_used_bytes` in the stats next to the existing
> field would make the account observable. That is a request, not part of this patch.
